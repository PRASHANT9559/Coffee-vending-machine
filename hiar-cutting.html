4. Supabase Realtime (The Magic)

Customer app is mostly a viewer. Realtime makes the tracking screen feel alive.

sequenceDiagram participant C as Customer App participant S as Supabase Realtime participant P as Partner App participant DB as Postgres Note over C,S: Customer opens tracking screen C->>S: Subscribe to channel 'booking-2847' S-->>C: Subscribed loop Every 15 seconds P->>DB: UPDATE partners SET current_lat=..., current_lng=... DB->>S: postgres_changes event S-->>C: Push update C->>C: Move map marker end P->>DB: UPDATE bookings SET state='at_location' DB->>S: postgres_changes event S-->>C: State changed C->>C: Show PIN screen P->>DB: UPDATE bookings SET state='in_service' DB->>S: postgres_changes event S-->>C: Service started P->>DB: UPDATE bookings SET state='completed' DB->>S: postgres_changes event S-->>C: Open rating modal

🎯 Realtime Channels

// Subscribe to booking updates
final channel = supabase.channel('booking-${bookingId}');

channel.onPostgresChanges(
  event: PostgresChangeEvent.update,
  schema: 'public',
  table: 'bookings',
  filter: 'id=eq.$bookingId',
  callback: (payload) => updateUI(payload.newRecord),
);

channel.onPostgresChanges(
  event: PostgresChangeEvent.update,
  schema: 'public',
  table: 'partners',
  filter: 'id=eq.$partnerId',
  callback: (payload) => moveMarker(payload.newRecord),
);

channel.subscribe();

6. Row Level Security (CRITICAL)

Customer can ONLY access their own data. Enforced at database level.

🔒 Customers Table

-- Users see only their own row
CREATE POLICY "Users view own profile" 
  ON customers FOR SELECT 
  USING (id = auth.uid());

CREATE POLICY "Users update own profile" 
  ON customers FOR UPDATE 
  USING (id = auth.uid());

📋 Bookings Table

-- Users see only their own bookings
CREATE POLICY "Users view own bookings" 
  ON bookings FOR SELECT 
  USING (customer_id = auth.uid());

CREATE POLICY "Users create own bookings" 
  ON bookings FOR INSERT 
  WITH CHECK (customer_id = auth.uid());

📍 Addresses

-- Users manage only their own addresses
CREATE POLICY "Users manage own addresses" 
  ON customer_addresses 
  FOR ALL 
  USING (customer_id = auth.uid());

🌍 Services (Public Read)

-- Anyone can browse services
CREATE POLICY "Services are public" 
  ON services FOR SELECT 
  USING (is_active = true);

-- No one writes from client
-- (admin uses service role key)

7. Edge Functions (Deno)

Server-side logic that can't run in the client.

💳 create-payment-intent

Called before opening Stripe sheet

  • • Get/create Stripe customer
  • • Generate ephemeral key
  • • Create payment intent
  • • Idempotency key handling

🚗 dispatch-job

Triggered after payment success

  • • Find nearest online partners
  • • Score by rating + distance
  • • Send job offer via FCM
  • • 60s timeout + retry

🔔 send-push

Wrapper for FCM

  • • Look up push tokens
  • • Compose notification
  • • Send via FCM API
  • • Handle invalid tokens

📅 get-available-slots

Returns bookable time slots

  • • Check partner availability
  • • Filter by service area
  • • Account for travel time
  • • Return 1-hour intervals

📄 generate-invoice

After service complete

  • • Generate PDF with 19% VAT
  • • Upload to Storage
  • • Email to customer
  • • Save URL in booking

💸 process-refund

On cancellation

  • • Calculate refund amount
  • • Call Stripe refund API
  • • Update booking state
  • • Notify customer + partner

9. Customer vs Partner App — Comparison

Aspect Customer App Partner App
Primary Role Browser + Payer + Viewer Action-taker + Service executor
State Machine Simple (7 states, mostly read) Complex (7+ states, action-driven)
Realtime Usage High (tracking, partner location) Medium (job offers, status updates)
Background Services Low (FCM only) High (GPS, foreground service)
Payment Role Payer (Stripe customer) Recipient (Stripe Connect)
Key Feature Live tracking with map Job offer with 60s timer
Permission Focus Location (while using), Notifications Background location, Camera, Storage
Critical UX Booking completion rate Job acceptance rate
